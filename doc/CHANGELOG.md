### 2026.09.25 修复：批量标定不能跨会话保存（关掉应用就得重新逐个框）

**问题**：批量面板的「保存标定」只写内存 `state.batch_calibs`（`on_batch_save_calib()` 没有任何磁盘写入）。标定唯一能落盘的途径是**跑完一次检测**（写历史记录时顺带存 `hoop` + `baseline_idx`），而回填只从历史记录取。于是：20 个视频标到一半关掉应用 → 全丢；没跑过检测的视频每次加载文件夹都显示 ○未标定。

**实测证据**：`Y:\全场录像\2026.07.29` 加载后日志 `[CALIB] 从历史记录回填 1/4 个视频的篮筐标定` —— 只有跑过检测的第 4 个恢复，另外三个从没跑过，历史里没有框可回填。

**实现**：
- 新增 `cache/batch_calibs.json`（`{视频完整路径: {hoop, baseline_idx}}`）；`state.upsert_batch_calib()` 读-改-写单条（保留其余视频的标定），原子写沿用 `_atomic_write_json`
- `on_batch_save_calib()` 落盘；写盘失败时状态栏追加「（写盘失败，仅本次会话有效）」，不阻断内存标定继续可用
- 回填改成三级优先级：**本次会话内存 > 落盘缓存 > 历史记录**，两级分别打日志「从批量标定缓存回填 N 个」「从历史记录回填 N 个」，便于排查标定从哪儿来；函数随之改名 `backfill_batch_calibs_from_history()` → `backfill_batch_calibs()`（名字里的 from_history 已不再准确）
- 坏数据一律跳过、不报错：`hoop` 不是 4 个数 / 条目不是字典 / JSON 损坏 → 忽略该条（列表显示 ○未标定）；视频被移动改名时路径对不上，自然落到「跳过」（路径是唯一键，**不做 basename 模糊匹配** —— 不同文件夹的同名视频会串框）

**代价**：每个视频约 80 字节，不做自动清理（无法区分「网络盘暂时未挂载」和「视频已删除」，误删会逼用户重标）。

**验证**：新增 16 例测试（落盘往返 / 合并保留 / 坏数据跳过 / 三级优先级 / 改名跳过 / 无 batch_files 早退），全量 262 passed。

### 2026.09.22 新增：HDR 源在「给人看」的产物上做真正的 SDR 映射（识别仍读源文件）

**背景（承接下一条）**：下一条「10-bit .mov 的预览片段播不了」把预览钉到 8-bit，解决了「浏览器播不了」；但那只是**位深降级**——BT.2020 原色被当 BT.709 用，球场青/粉明显偏淡。本次补上真正的 HDR→SDR 映射。

**边界（用户明确要求）**：映射只作用于**预览片段与集锦/单球导出**；**检测与特征抽取一律直接读源文件**、不做任何色彩转换——口径一动，历史分数与片段缓存就全失去可比性。

**实现**：
- `video_io.is_hdr_source()`：读 `codec_context.color_trc`，`16(PQ)` / `18(HLG)` 判 HDR；读不到/未知/异常一律 False（误判成 HDR 会把 SDR 整场压暗，反向只偏淡）
- `cutter.build_view_filter(src, scale=None)`：HDR → `HDR_TO_SDR_FILTER`；SDR → 预览只钉 `setparams` 标记、集锦保持「不加滤镜」的既有路径
- 接线：预览每场只探测一次、与打点探针共用同一串滤镜（时序口径不失真）；`cut_clips` 按源判定并**缓存**——整场四节合并导出时可能混着老 SDR 录像，而逐段重开容器探测会白花时间（实测本地 14~18ms/次、网络盘 47~123ms/次）

**映射链的实测取值**（`1st quarter vs 悍高.mov`，HLG 24 分钟；同屏对照见 `cache/_hdr_cmp/`）：

| 候选 | mean | p99 | 爆白 |
|---|---|---|---|
| 不映射（下一条的现状） | 150 | 234 | 0.01% |
| 教科书 hable npl=1000 | 63 | 130 | 0 |
| 纯色彩学转换（无 tonemap） | 193 | 255 | **17.5%** |
| mobius npl=400 param=0.5 | 135 | 227 | 0 |
| **选定：hable npl=400 + curves** | **113** | **199** | **0** |

最终链：`zscale=t=linear:npl=400 → format=gbrpf32le + tonemap=hable:desat=0 → zscale=t=bt709:m=bt709:r=tv → curves=all='0/0 0.5/0.62 1/1' → format=yuv420p`

- `npl=400`：HLG 的 OOTF 系统 gamma 随标称峰值变（400nit → γ≈1.03，接近线性），实测这个值既不压暗也不爆白；教科书常用的 npl=1000 会把中间调压到 mean 63/255
- `curves` 而非 `eq=gamma`：后者提中间调时把黑场一起抬起（实测 p1 12 → 36，暗部发灰）
- **BT.2390 用不了**：打包用的 imageio-ffmpeg v7.1 静态版**没编 libplacebo**，而 BT.2390 只有 libplacebo 实现；原生 `tonemap` 只有 none/linear/gamma/clip/reinhard/hable/mobius。`mobius` 属同族膝盖曲线（实测 mean 135、更亮、零爆白），已实测记录在案——将来若换带 libplacebo 的 ffmpeg 构建，可直接切 BT.2390

**代价**（同源实切，libx264 软编）：预览 480p 1.1s → 1.8s（+0.7s/片段）；集锦 1080p 7.4s → 11.5s（+4.1s/段，约 +55%）。

**验证**：预览 480p / 集锦 1080p × HDR/SDR 四条产物全为 `yuv420p / bt709`；服务重启后真实单球导出实测 mean 114.3 / p99 199 / 爆白 0%，与离线口径一致。新增 8 例测试（HDR 判定、异常侧保守、滤镜四态、预览接线守卫），全量 233 passed。

### 2026.09.22 修复：手机 HDR 源（10-bit .mov）的预览片段在浏览器里播不了

**现象**：`E:\ball\1st quarter vs 悍高.mov` 检测跑完（70 个候选中 15 个自动 √）、片段也都切好了（`cache/demo_output/goal_*.mp4`，每个 0.35~0.5MB、PyAV 能正常解 177 帧），但点卡片上的「预览」**什么都不播**——没有报错、没有 404、日志里也查不到任何异常。

**根因**：片段的编码 profile 浏览器不认。源是手机直出的 HDR：

```
hevc (Main 10), yuv420p10le, bt2020nc/bt2020/arib-std-b67   ← HLG / 10-bit
```

两个条件同时成立才踩到：① 源是 10-bit HLG；② 本次 NVENC 全程失败（`No capable devices found`，70/70 回退软编）。而 `build_encode_args` 的软编分支只给 `libx264 -crf`、**没有 `-pix_fmt`**，libx264 就按输入位深原样编出：

| | 修复前 | 修复后 |
|---|---|---|
| profile | **h264 High 10** | h264 High |
| pix_fmt | **yuv420p10le** | yuv420p |
| 颜色标记 | bt2020 / arib-std-b67 | bt709 |

Chrome 的 H.264 解码链只吃 8-bit，遇到 High 10 **不报错、只黑屏**。既有的 Y: 盘录像全是 8-bit SDR（`h264 High/Main, yuv420p, bt709`），所以这个问题一直没暴露。对照证据（同一台机器、同一套 UI）：

```
goal_57_1273s_1790055947.mp4   h264 (Main)     yuv420p     bt709   ← Y盘源，能播
goal_69_1446s_1790083337.mp4   h264 (High 10)  yuv420p10le HLG     ← 本次 .mov，播不了
```

**修法**：`build_encode_args` 两条分支统一追加 `-pix_fmt yuv420p`（`cutter/ffmpeg_cutter.py`）；预览切片的 `-vf` 追加新增的模块常量 `SDR_TAG_FILTER`（`setparams=colorspace=bt709:...`）——`-color_primaries/-color_trc` 这两个输出选项在这条链路上不生效（libx264 写进 colr box 的值取自帧属性，会被输入侧 HDR 标记盖住，实测仍是 bt2020/arib-std-b67），只有改帧属性才落地。打点探针的 `-vf` 同步（否则「切片墙钟 − 探针」的编码耗时口径失真）。

**实测**：HDR `.mov` 与 SDR `.mp4` 两条源现在都产出 `yuv420p / High / bt709/bt709/bt709`；已用历史里的精确时间戳按原文件名就地重切这 70 个片段（105s，70/70 成功），服务内存里的 clip 路径不变、点预览即可播。全量测试通过（`build_encode_args` 另有 `TestPreviewTiming` 覆盖）。

**已知取舍**：HLG→SDR 目前是朴素转换（只降位深 + 改标记，没做 tone mapping），画面可能偏灰/偏亮。要做正确映射需按源的 `color_trc` 判定后启用 `zscale`+`tonemap` 链（本机 ffmpeg 带 zscale）；等遇到实际观感投诉再加。

### 2026.09.22 新增：历史记录留档 AI 当次分带（`verify_snapshot`）

**问题**：人工确认（点「预览」即视为复核过，或点 √/×）会把 clips 的 `mark_source` 从 `auto` 提升为 `manual`，随后 `labels.auto_kept` / `auto_rejected` 被整批搬进 `kept` / `deleted`——**模型当次判了什么从此在历史里查不到**。「AI 判对率」只能靠标定前临时抓一份快照，忘了抓就永久丢失（本场 1st quarter vs 悍高.mov 就只剩一次 21:32 的临时快照可比：高带 13/13 全对、低带 41/41 全对、中间带 16 条里 5 真球 11 误报、人工量 70 → 16）。

**修法**：历史记录新增只写一次的 `verify_snapshot` 字段，在 `add_history` 那一刻写入（`detection._build_verify_snapshot`）：

```json
{"keep_thr": 0.68, "reject_thr": 0.15,
 "weights": {"lgbm": 0.5, "b": 1.0, "flow": 1.0, "vm": 0.5},
 "fingerprint": "<model_fingerprint()>",
 "auto_kept": [...], "auto_rejected": [...],
 "scores": {"16.373": 0.91, ...}}
```

- 写在 `add_history` 而不是 `_sync_marks` 之后：那之后 `auto_*` 就已被人工确认搬走了
- `update_history_labels` 是读-改-写、只动 `labels` 段，所以整个标定过程都不影响这份快照
- 存**逐片段分数**而非只存两个 ts 列表：以后换 `keep_thr`/`reject_thr` 想回看「换个阈值会怎样」，直接拿分算，不必重跑 7 分钟复核
- 只认 `mark_source == "auto"`，人工判过的不进模型的成绩单；AI 复核没跑（clips 上没有 `score`）返回 `None`，字段不入库
- 类型校验放在写入处（`state._cast_verify_snapshot`）：留档字段写坏了要等几个月后跑统计才发现，那时数据已经没了
- 留档失败只记 warning，不影响检测结果落盘

**回填**：本场（标定已完成，`auto_*` 已被搬走）按 21:32 的临时快照回填了一份，`scores` 为空 + `backfilled: true`（当次分数未落盘，不可恢复）。写入前有 7 项一致性校验（两带条数 13/41、不重叠、都属本场进球、高带 ⊆ kept、低带 ⊆ deleted、13+41+16=70、字段不存在）。

**测试**：新增 5 例（快照在人工确认后仍在 / 非 dict 拒绝 / 三带与分数口径 / AI 未跑返回 None / run_detect 接线守卫），全量 222 passed。

### 2026.09.22 修复：加载 `E:\ball\*.mov` 永久卡死（PyAV 帧线程死锁）+ `start.bat` 输出链路冻住服务

**现象**：选 `E:\ball` 下的 `.mov` 点加载，UI 停在「正在加载 …」不再推进；进程 CPU 0%、日志一行不写、TCP 仍能连上、HTTP 不响应。同一序列里 `.mp4` 都正常。

**根因**：PyAV 帧级多线程解码死锁。用 py-spy 抓 worker 栈停在 `detection.py:2209`，原生栈是 `SleepConditionVariableSRW`（avcodec 帧线程池的条件变量）。二分确认触发条件：**同一进程里先跑过 torch/CUDA 的 YOLO 推理**，再解特定 `.mov`（实测 HEVC/QuickTime 1920x1080）→ 必现；`read_frame`（含 seek）是唯一入口，cv2 无关、`.mp4` 不触发。触发率实测（同序列各重复 4 次）：默认帧线程 **4/4 卡死**、`thread_count=1` → **0/4**。

**修法**：`video_io.read_frame` 里 `stream.codec_context.thread_count = 1`（附现象与实测数据注释）。**检测主路径的 `VideoReader` 未加**——它会从 92 帧/秒降到 40 帧/秒；代价是解这类 `.mov` 会挂进程退出，属已知遗留。

**次因（独立的问题，同一现象加成）**：`start.bat` 用 PowerShell 管道转发 stdout（`& python ... | ForEach-Object { Write-Host $_ }`），控制台一旦停止消费输出（QuickEdit 选中文本、或被不读输出的父进程拉起），python 下次写 stdout 就阻塞——而应用是从事件循环线程记日志的，**整条事件循环随之冻住**：TCP 能连、HTTP 不回、CPU 0%、日志一行都没有。改用 cmd 直接 `>>` 重定向到日志文件，去掉管道耦合（`Tee-Object` 也不可用：PS 5.1 一律写 UTF-16LE）。

**验证**：`read_frame(帧0)` 3/3 正常（0.13s）、完整加载路径正常返回、全量测试通过、服务重启后 HTTP 200。

### 2026.09.21 修复：连续 87 秒的误报——静止假球让 YOLO 硬否决长期失效

**现象**：`2026.09.21-4th.mp4` 在 **281~368s 连续 87 秒出 39 个候选**（人工标了 35 个 ×），几乎每 2.1 秒一个，正好贴着 `min_gap_sec=2.0`。

### 2026.09.21 修复：单球「导出」点了没反应（跨任务后调 `ui.download` 抛 slot 异常）

**现象**：结果卡片上点「导出」，片段其实**已经切好了**（NVENC 跑完、文件已落盘），但浏览器收不到下载，UI 上表现为「点了没反应」。当日日志里该异常出现 **16 次**。

```
RuntimeError: The current slot cannot be determined because the slot stack for this task is empty.
This may happen if you try to create UI from a background task.
```

**根因**：NiceGUI 的 slot 栈按 **asyncio task id** 存（`nicegui/slot.py: Slot.stacks`），而 `asyncio.create_task(_run_export_clip(idx))` 起的是**新任务**，新任务的栈是空的。`ui.download` 内部要 `context.client → slot.parent.client`，必须先能确定当前 slot → 抛异常，下载消息根本没发出去。事件处理器自身是有栈的（`nicegui/events.py: handle_event` 用 `with parent_slot:` 执行处理器），问题只出在**跨任务之后**。

**修法**：照 NiceGUI 自己的做法（`events.py::_await_and_handle_in_context` 同样先捕获 `parent_slot` 再 `with`）——在处理器里取走 `context.slot` 传给任务，任务内 `with slot:` 后再调 `ui.download`。

**验证**：重启服务后再次导出，日志无 slot 异常、片段正常产出（`cache/demo_output/2026.09.21-4th-goal-1273.1s.mp4`）。
未加单测：该路径需要跑起来的 NiceGUI 应用（本仓库单测均为纯逻辑层），以服务日志实测为准。

main 与分支同源修复（`68c2e8f` / `5d444ca`）。

### 2026.09.20 预览切片打点：结论「切片不慢」，并修掉把它记成瓶颈的计时口径

**动机**：此前从日志的 `preview X min` 推断「预览片段是第二大成本、每片段 6~9s、瓶颈在读网络盘源/解码」，但那个数字是代码推的，没有实测支撑。

**打点**（`services/detection.py`，默认关闭）：

- `_run_cut` 返回 `(等锁秒, ffmpeg 墙钟秒)`：等锁 = 拿 NVENC 信号量的排队时间（信号量把整条 ffmpeg 含读源/解码都圈在里面，所以这两段互斥）
- `_preview_recs` 由 `_cut_one` 在 `finally` 里留档（成功/空文件/失败/回退全记），NVENC 失败回退软编置 `fallback`
- `_preview_timing_summary()` 每场固定打一行：片段数、ffmpeg 合计、等锁合计与占比、两者中位/最大、回退次数
- `PREVIEW_PROFILE=True` 逐片段打明细；`PREVIEW_PROBE_N=N` 对前 N 个片段额外跑一次「同样 `-ss/-i/-vf` 但输出 `-f null -`」的探针，`切片墙钟 − 探针 ≈ 编码`

**实测（08.31-3rd，38 片段）**：`ffmpeg 合计 58.0s | 等锁 0.0s（0%） | ffmpeg 中位/最大 1.52/1.86s` —— 2 路并行约 29s 墙钟，**切片根本不是瓶颈**，等锁为 0 也说明 NVENC 会话配额没有排队。

**被证伪的旧结论**：08.31-2nd 日志的 `preview 5.2 min` 里，**4.6 min 是四臂 AI 复核**（同场 `[VERIFY] ... 耗时 276s`），切片只占约 0.6 min。原因是 `_preview_elapsed = _t2 - _t1`：`_t1` 之后依次是切片 → AI 复核 → 缓存落盘/断点清理，三者被合并进同一个桶。`_t1` 之后真正的成本大头是 A 臂逐帧 YOLO（约 6.5s/候选）。

**口径修正**：`Timing` 行拆成 `detect + preview + verify + tail`，四项之和仍等于 total（账平）；`preview` 现在只表示切片。

**测试**：`tests/test_preview_timing.py`（8 例）——汇总行格式 4 例（含全失败不崩、探针占比、回退计数）+ 接线 4 例（假 ffmpeg 验证等锁/墙钟/回退/探针确实进了记录、摘要确实被打印）。全量 177 项通过。

### 2026.09.20 裁剪推理：只推筐接受框（imgsz 1280 → 640），单场实测耗时 -34%

**动机**：上一条的门槛修复让 YOLO 调用从最坏 897 次涨到 6181 次、检测耗时 +63%；而单次推理 45 ms 里绝大部分花在整帧 1920×1080 → 1280 的 letterbox 上，画面里绝大多数像素与「筐附近有没有球」无关。

**做法**：`ball_pos` 的唯一消费方是 `_check_yolo_near_hoop`，它只关心
`GoalDetector.yolo_accept_box()` 这个范围（横向 ±1.5×hoop_w、上 1.0×、下 2.0×hoop_h）。于是：

- 接受框几何抽成 `GoalDetector.yolo_accept_box()` 单点维护，判定端与检测端共用，避免两处几何漂移
- 推理输入改为「接受框 + 20% 外扩」（各场实测约 500×580），`imgsz` **1280 → 640**
- 球在输入里的像素从 13-20px 提升到 ~22-33px（缩放 1.1 > 整帧路径的 0.667）——这正是历史上从 960 提到 1280 要解决的问题，裁剪反而改善了它
- 检出框平移回整帧坐标（接受框判定用整帧坐标）；区域外的远端误报天然落在输入之外，是 argmax 修复之外的第二道保险

**验证（09.11-1st，17.9 min，YOLO 调用最多的场次；同门槛同参数，只切输入路径）**

| 指标 | 整帧 1280 | 裁剪 640 | 变化 |
|---|---|---|---|
| 总耗时 | 9.1 min | **6.0 min** | **-33.9%** |
| 候选数 | 54 | 54 | 0 |
| 真球命中 | 19/19 | 19/19 | 0 |
| 误报被检 | 25/25 | 25/25 | 0 |
| 上方 / 冷却拒 / YOLO确认 | 75 / 3240 / 54 | 75 / 3240 / 54 | 0 |

候选集合逐一对上，仅 1 处时间戳漂移（`524.09 → 523.02`，Δ1.07s，本身是低带 score 0.058）。

**微基准（同帧同模型，仅换输入路径）**：整帧 1280 = **45.08 ms/次**；裁剪 640 = 21.56 ms；裁剪 512 = 15.77 ms。只降到 2.1x 而非 4x（像素量是 4x），是因为有 ~14 ms/次 的固定开销（拟合 `T ≈ 19.1 ms/Mpx × 像素 + 13.8 ms`），裁剪消不掉——要再快需换 ONNX/TensorRT。

**与门槛修复叠加（09.11-1st）**：5.2 min（门槛修复前）→ 8.5 min（仅门槛）→ **6.0 min**（+裁剪），即裁剪把门槛修复的耗时代价基本买回来，同时保留「斑块能触发 ⇒ YOLO 必已跑过」这个不变量。

**测试**：`tests/test_yolo_crop.py`（20 例），核心断言是**裁剪框必须 ⊇ 接受框**（否则会重现「球在筐附近、却不在推理输入里」的静默漏检）、缩放不得把球缩小、坐标映射可逆、退化框回退整帧；`tests/test_yolo_accept_box.py` 验证几何抽取行为等价。全量 169 项通过。

### 2026.09.20 条件跳过门槛改为与斑块门同构（+ 预热基准改动：实测后不启用）

上一条遗留两处的处置：**第 2 处（条件跳过门槛严于斑块门槛）已修复上线**；**第 1 处（预热基准与主循环不一致）已完整实现并实测，结论是不启用**，理由见下。

#### ① 已上线：门槛改为「同二值化 + 同形态学 + 只留面积下限」

- 旧实现要求「超阈值像素 > 搜索区总像素的 1%」（本片 ≈715px），而 `_find_moving_blob` 的下限只有 `min_blob_area=30` —— 落在 30~715px 之间的真球会「斑块触发了、YOLO 却从没在附近跑过」→ `_check_yolo_near_hoop` 必然判否。
- 新实现与斑块检测器用**同一套二值化 + 同一套形态学**（`MORPH_OPEN` + `MORPH_CLOSE`），只保留面积下限，去掉宽度与圆形度过滤（那两道是「选球」用的，不该决定「要不要跑 YOLO」）。由此得到可断言的不变量：**`_find_moving_blob` 找得到 ⇒ 门槛必为真**。
- 常量 `MOTION_PIXEL_RATIO` 删除（不再按像素占比判定）。

| 候选 | 39 | 40（+1，低带自动×，不占人工） |
| 真球命中 | 15/15 | **15/15，时间戳一个没动** |
| 分带 | 高12 / 中15 / 低12 | 高12 / 中15 / 低13 |

回归测试 `TestMotionGateInvariant`（6 例，含「小球像素占比远小于 1% 时门槛仍须为真」——该例在旧实现下必然失败）。全量 **149 项通过**。

#### ② 不启用：预热基准改为「视频内最静止的一帧」+ 预热期滚动刷新

- **问题属实**：预热 30s 内 `rolling_baseline_sec=60` 从不触发，且滚动更新块位于预热 `return None` **之后** → 预热量到的永远是「标定帧 vs 视频」的陈旧噪声。
- **实现并实测**：预热前扫前 2s 取运动量最小的一帧作初始基准（本片取到第 13 帧），预热期按 `WARMUP/4` 刷新基准。效果与预期完全一致：**阈值 50 → 13、P95 73.1 → 5.0**。
- **但代价大于收益，决定不启用**：

|---|---|---|
| 候选 | 39 | 60（+21） |

| 分带 | 高12 / 中15 / 低12 | 高11 / **中20** / 低29 |

| YOLO 推理 | 1147 次 | 5575 次 |
| 检测耗时 | 4.5 min | 9.6 min |

  机制：`阈值 = median(P95) + 8` 这个常数、以及斑块过滤器（面积/圆度/宽度），都是在**被抬高的噪声尺度**上调出来的。单独修正测量而不配平下游，系统就变成「一有动静就触发」——冷却拒绝 2287 → 3547，状态机被多出来的垃圾触发挤偏，两个真球（`493.91`、`818.46`）的时刻漂移 0.8~1.3s，超 `_LABEL_REMAP_TOL_SEC=0.5` 会被丢标签。
- **重新启用前需要**：① 与斑块过滤器一起重新配平（或给阈值下限兜底）；② 在 2~3 场其它视频上验证候选数不失控。
- **已知陷阱（保留记录）**：`tracker.py` 的 `rolling_baseline_sec` 在**预热期不生效**（滚动更新块位于预热 early-return 之后）。将来若改预热策略，必须同时把该块移到预热判断之前，否则参数是死的。

### 2026.09.19 四臂集成 AI 复核（自动 √）

检测出候选后自动跑一遍「四臂集成」打分，达标候选直接标 √ 免人工确认。**只标记、不删除任何候选**，人工标记永远优先。五场真实录像实测：186 个候选里自动 √ 53 个，**精度 100%**，召回 70.7%。（后续 Flow 臂也换成域内自监督骨干，阈值重标为 0.68；六场实测自动 √ 精度 0.988 / 召回 80.6%，见第七节）

#### 一、四臂构成与线上接入（提交 `f110efd`）

四臂为 **A**（手工特征 LightGBM）+ **B**（SimCLR 时序）+ **Flow**（光流）+ **VM**（VideoMAE），构成与预处理口径见 [ALGORITHM.md](ALGORITHM.md#ai-复核四臂集成打分)。线上实现为 `services/goal_verifier.py`：

| 设计点 | 做法 | 原因 |
|---|---|---|
| 只标记不删候选 | 只写 `clip["auto"]` / `verify_score` | 漏球代价远大于多标一个，低分候选照常人工确认 |
| 人工优先 | 只写 `mark_source != "manual"` 的片段 | 用户判过的 × 不能被模型高分翻成 √ |
| 口径指纹 `verify_ver` | 模型 mtime + 权重 + 阈值 的哈希 | 换骨干/调权重/改阈值后旧分数失效，否则会用**新阈值去套旧分**给出错误判决 |
| 分数随片段缓存落盘 | `state.py` 的 `_AI_CACHE_KEYS` | 原先只存 ts/path/idx，服务重启后徽标整批消失 |
| 复核阶段上报进度 | 按批回调（A 臂每 8 个候选） | A 臂逐帧 YOLO 是瓶颈（5~6.5 秒/候选），原先界面静默数分钟像卡死 |

#### 五、已知边界

- **绝对阈值不跨场稳定**：`2026.09.03-3rd`（6.3 分钟短片段）排序完美（AUC 1.0，3 个进球全部排在 11 个误报之上），但所有视觉臂的绝对分整体偏低 0.2~0.6（VM 的 √ 均值 0.889 → 0.257），阈值 0.72 下一个都过不了，**本场收益为 0**。目前观察到的漂移诱因是「短片段」；同日同时段的 33 分钟长视频（09.03-4th）各臂分离度正常。
- **评估过但未启用的备选规则**：分位保底（`分数 ≥ 0.72` 或 本场前 10%，并加分数下限 0.5）。五场 186 个候选上精度仍为 100%、召回 70.7% → 73.3%，但 `max(1, …)` 意味着**每场都强制自动通过至少 1 个**，在进球率低于 10% 或 0 进球的场次可能凭空产生错误 √，而这类样本目前一场都没有。故先攒数据再定。
- **自动 √ 会改变导出范围**：导出规则是「有 √ 只导 √」，若不复核直接导出，只会导出自动通过的那些候选。
- **批量回看路径的复核已补齐**（本轮补）：批量识别本身走 `run_detect`，检测时就已打分；缺的是「重开程序后从流水线下拉框回看历史视频」这条路径（`_on_batch_load_video_impl`），它原先只回填 √/× 与人物——命中片段缓存的分是**旧阈值**算的，未命中缓存重新生成的片段则**一个分数都没有**，确认界面看不到任何 AI 徽标。现补上与单视频历史加载同口径的处理：`invalidate_stale` → 缺分补跑 / 有分 `refresh_auto` → 落盘缓存 + `_sync_marks`。
- **快照徽标不随阈值刷新**：流水线快照（`state.batch_results`）里的 `auto` 是检测当刻阈值的产物。改 `keep_thr` 后不重启程序的话，快照卡片仍是旧判决；重新点一次视频走历史分支才会刷新。

#### 八、VM 臂换头实验（未部署，如实记录否定结论）

VM 是四臂里最弱的一环（OOF 0.8208）。分诊发现两处浪费：① 特征是 `last_hidden_state` 的**全 token 均值池化**，把 16 帧（8 个 tubelet 时序位置 × 196 空间块）的运动结构整体拍平，VideoMAE 的时空自注意力等于没用上；② 头是 LGBM 且**只用 orig 特征**（未用增强变体）。

于是给 `extract_videomae.py` 加 `--temporal`（按 token 索引 `t*196+h*W+w` 复形后对空间取均值 → `(8,768)`），并写 `train_vm_head.py` 在同一分折/增强协议下把 5 种头一次比完：

| 候选头 | VM 单臂 AUC | 集成 AUC | p95 工作点召回 |
|---|---|---|---|
| LGBM（线上现状） | 0.8208 | 0.9640 | 0.783 |
| mean + pool 头 | 0.8633 | 0.9722 | 0.809 |
| mean + bigru 头 | 0.8556 | 0.9715 | 0.835 |
| temporal + bigru 头 | 0.8523 | 0.9724 | 0.858 |
| **temporal + pool 头** | **0.8839** | **0.9741** | **0.850** |

**OOF 上全面改善**（单臂 +0.063、集成 +0.010、p95 召回 +6.7pt），与 Flow 换骨干同量级。但**八场真实视频上没有兑现**：

| 配置 | 8 场 AUC | 同等精度（各 1 个误报）下的召回 | 4 场干净留出的召回 |
|---|---|---|---|
| 旧 LGBM 头 | 0.9858 | **83.5%**（112 自动√） | 70.0% |
| 新时序头 | 0.9856 | 73.7%（99 自动√） | **78.0%** |
| 两头平均 | 0.9862 | 77.4%（104 自动√） | 74.0% |

- AUC 三者持平（0.9856~0.9862，差在噪声内）
- 固定精度下**旧头反而多 13 个真进球**；新头只在 4 场干净留出上占优（+4 个），但一旦按 8 场匹配精度，这点优势也消失
- 机制：新头的分数更饱和，工作点对阈值极敏感（同一配置 0.72→107 个自动√、0.74→99 个，跨 0.02 就差 8 个），而线上是单点全局阈值

**决定：不部署**。服务端接线已回滚，`model_fingerprint()` 也回到原值（`1b9f0349d9a3`，与缓存一致 → **不触发任何重算**）。实验产物留在 `training/exp_vm_head/`（时序头检查点、OOF、8 场逐片段打分与复现脚本），`extract_videomae.py --temporal` 与 `train_vm_head.py` 保留可复跑。

**复核时修正的一处误判**：本节初稿曾断言「831 事件的 OOF 候选集与线上片段几乎不重叠（八场仅 12.9% 能匹配）」，并据此把「重建训练集」列为最优先事项。复核数据集构成后发现**该结论错误**——当时的比对脚本把「该视频不在训练集里」误当作「ts 不匹配」，也没考虑重新检测造成的亚帧位移。实际情况：

| 关系 | 情况 |
|---|---|
| 标注池（`cache/history`） | **25 场 / 995 片段**（正 396）——即日常标注的全部产出，且仍在增长 |
| 训练集 `dataset_v1` | 831 / 21 场 —— 是标注池的**子集**，不是另一批候选 |
| 候选空间 | **17/21 场 ts 逐一完全相同**；4 场在训练集冻结后被重新检测：09.01-1st、09.03-4th、09.04-1st 边界微移（<0.2s），**09.04-2nd 从 59 个片段增至 100 个** |
| 只在标注池里的 | 4 场 125 片段：08.31-1st、09.01-3rd、09.01-4th、09.03-3rd（即前文所谓「4 场干净留出」） |
| 只在训练集里的 | 无 |

所以「OOF 涨、实测平」的原因不是候选集不同，而是：① 训练集落后于标注池，且有 4 场视频重检后片段集已变——这部分候选任何模型都没见过；② 判定所用「各 1 个误报」是由 1~2 个片段决定的统计量，噪声极大。**VM 换头的最终判断因此接近五五开**：4 场留出场（唯一完全未参与训练的子集）两种头都恰为 1 个误报，新头召回 78.0% vs 旧头 70.0%，支持新头；八场合计在匹配精度下旧头多 13 个真进球。两个方向的差异都只有几到十几个片段，**不足以支撑一次会让全部缓存失效的部署**，故维持不部署，留待标注池扩充后再评。

**修正后的建议**：不是「重建」，而是**定期从标注池刷新训练集**（当前 831/995，且含已重检的旧片段），新标注的视频优先纳入；但**不要把 4 场留出场吃进训练集**——那是目前唯一的无偏验证来源。

**顺带修正阈值**：现役 LGBM 头在 8 场上的细扫描显示，阈值 **0.66** 明显优于现役 **0.68**——同样 1 个误报，自动√ 从 109 增至 112，召回 81.2% → **83.5%**（4 场干净留出不受影响：两者都是 36 个 / 70.0%）。本轮不改（避免再触发一次全量重算），留给下次标定一并处理。

#### 九、训练集从标注池重建（831 → 870）与刷新后重算

第八节复核时发现：`dataset_v1.json`（2026.09.18 冻结快照）已落后于标注池，且 4 场视频在快照后被重新检测过。本节把训练集改为**直接由 `cache/history` 的标注池重建**（`build_dataset.py` 保留了 `--from-blocks` 以复现历史数字）。

| | 值 |
|---|---|
| 标注池 | 25 场 / 995 片段（正 396） |
| 训练集（排除 4 场留出后） | **870 事件**（正 346 / 负 524 / 21 场） |
| 相对旧快照 | 沿用 793 / 新增 77 / 移除 38 / 标签纠正 1 |

**event_id 沿用策略**：重新检测会让同一进球位移 0.03~0.17 秒，帧号随之改变、`event_id` 也就变了——照搬就会白白重抽全部特征（215 个）。故按 0.25 秒容差对齐旧 `event_id`（远小于检测侧 `min_gap_sec=2.0`，不会误并），需新抽的特征从 215 降到 **77** 个。顺带自动捞到 1 个事后改过的标签（× → √）。

刷新后在**同一套按比赛日分折**上重算四臂 OOF（`refresh_oof.py`，只测量、不写任何部署产物）：

| 臂 | 刷新前（831） | 刷新后（870） |
|---|---|---|
| A(LGBM) | 0.8034 | 0.8085 |
| B(SimCLR) | 0.9217 | 0.9234 |
| Flow(SimCLR) | 0.9478 | 0.9397 |
| VM(LGBM 旧头) | 0.8208 | 0.8243 |
| VM(时序头) | 0.8839 | **0.8390** |
| 集成（VM=旧头） | 0.9640 | 0.9677 |
| 集成（VM=时序头） | 0.9741 | 0.9736 |

- 现役口径小幅改善（0.9640 → 0.9677），p95 工作点阈值 0.640 → **0.630**
- **VM 时序头的集成领先从 +0.0101 缩到 +0.0059**：它此前 0.884 的单臂成绩里，有相当部分是那套 831 事件的拟合产物。这与八场真实视频「同等精度下旧头召回更高」互相印证，**维持不部署**（见 `training/exp_vm_head/`）
- 结论：数据集刷新是必要的卫生工作（候选与当前检测对齐、标签纠正），但它不会把「五五开」的模型选择变成明确结论——**要判断模型改动，靠的是留出场上的新数据，不是把同一批数据换个方式切**

#### 十、三段分诊：把「追 100% 自动」换成「只看该看的」

**起因**：问「照这个训练能达到全部真球都识别吗」——用九场 419 片段算了完整权衡曲线，答案是不能：

| 阈值 | 自动√ | 误报 | 漏真球 | 精度 | 召回 |
|---|---|---|---|---|---|
| 0.68（现役） | 127 | 1 | 30 | 0.992 | 80.8% |
| 0.60 | 145 | 6 | 17 | 0.959 | 89.1% |
| 0.30 | 204 | 51 | 3 | 0.750 | 98.1% |
| **0.152** | **259** | **103** | **0** | **0.602** | **100%** |

要 100% 召回就得压到 0.152，那时 259 个自动√里有 103 个误报。根因：**最高误报分 0.781 之下压着 44.9% 的真球**（分布重叠，调阈值挪不开），且各场「最低真球分」从 0.152 到 0.670 跨 0.52（单点全局阈值不可能同时适配）。

顺带验证了「按场标准化」这条看似对症的路——**是平手，没采纳**：去掉各场漂移后高精度端反而更差（精度 0.99 下召回 83.3% → 64.7%），中段略好（0.95 下 89.1% → 89.7%）。绝对分里带着「这场整体像不像有球」的真实信息，标准化把它一起抹掉了。

**做法**：集成分按两个阈值分三带，人工只需复核中间带（`services/goal_verifier.refresh_auto`）：

| 带 | 条件 | 动作 |
|---|---|---|
| 高带 | `score >= keep_thr`(0.68) | `mark=keep` + `mark_source=auto` → 绿标「AI ✓」 |
| 中间带 | `reject_thr`(0.15) `<= score < keep_thr` | 不加标记 → 琥珀标「AI ?」，人工只看这一带 |
| 低带 | `score < reject_thr` | `mark=reject` + `mark_source=auto` → 红标「AI ×」 |

- `reject_thr` 读自 meta（原值 0.16 会把某场一个 0.152 的真球划进低带，改为 **0.15**）；它**不进口径指纹**——只影响标记不影响分数，`refresh_auto` 按缓存分重推，改它不触发重算
- 阈值调高后落回中间带的片段会**清掉模型标记交还人工**（旧实现只写不清，会留下"没人看却已被判定"的片段）
- UI：三色徽标（绿✓/琥珀?/红×）+ 统计行区分人工与 AI 计数 + **「只看待确认」开关**（隐藏已判定片段）

**标签库按来源分流**（`services/state.py`）：人工 × 进 `labels.deleted`，模型 × 进 `labels.auto_rejected`。混在一起会形成「模型自己判×→自己学」的闭环，且某个被漏判的难例会永久固化成负样本——重建训练集（`build_dataset.py`）只读前者。

**实测**（走服务端真实路径，4 场 200 片段）：高带 52（1 误报）/ 中间带 **62（31.0%）** / 低带 86（0 真球）→ 人工从逐 200 个降到只看 62 个。九场口径同：419 → **132（31%）**。

两个附带收益：塌陷场 `2026.09.03-3rd`（AUC 1.0 但高带 0 个）现在把 3 个真球浮到中间带，人工看 6 个而不是全部 14 个；`09.01-4th` 那个唯一误报仍留在高带（它是真误报，已被人工确认过）。

#### 十一、AI 识别总开关

`参数` 面板新增「AI 识别（四臂复核）」开关（默认开，`services/goal_verifier.set_enabled`）：

| 位置 | 关闭后的行为 |
|---|---|
| 检测（`run_detect`） | 整段跳过四臂复核：候选不带任何 `score` / `auto` / `auto_reject`，全部留人工判定；顺带省掉 A 臂逐帧 YOLO 的数分钟开销 |
| 历史回读 / 批量回看 | 跳过「缺分补跑 + `refresh_auto` + `_sync_marks`」，不为看结果触发任何推理 |
| 卡片 | AI 徽标不渲染；`mark_source == "auto"` 的标记按「未判定」呈现（统计行的 √/×/待确认与「只看待确认」同口径） |

**关闭是「不再跑」，不是「清掉已有结果」**：缓存里的分数、历史里的 `kept`/`deleted`/`auto_rejected` 一律不动，重开开关即时从缓存分恢复分诊（不重算）。`mark_auto` 内部另加一层兜底判断，防止将来新增调用点漏判开关。

验证：开关往返切换（服务端日志 `goal_verifier: AI 复核已开启/关闭`）、状态提示与徽标随动，浏览器控制台无报错；新增 2 项单测（关闭时不产分数、不清既有分数与标记）。

#### 十二、历史记录缺分数时，补跑前先问一句

加载历史记录时若片段缺 AI 分数（旧记录 / 当初关着 AI 识别 / 片段缓存失效要重新生成），原先会**静默**跑一遍四臂复核——分钟级开销（A 臂逐帧 YOLO 约 6.5 秒/候选），界面看着像卡死。现在先问：

- 加载前 `detection.history_missing_scores(video_path)` 只查历史记录 + 片段缓存（不生成预览、不碰 GPU、秒回），得出「缺几个 / 共几个」；缓存未命中时片段要重新生成，分数必然全缺
- 缺就问：「该记录 5 个片段里有 5 个还没有 AI 分数。补跑四臂复核约需 1 分钟；不补跑则片段全部需人工判定，之后重开这条记录仍可补跑」→「补跑 AI」/「直接加载」
- 选「直接加载」→ `on_load_history(..., ai_backfill=False)` 只加载不补跑：不产分数、不打标记，缓存与历史标签都不动，之后重开同一条记录还会再问
- 全局关掉「AI 识别」时跳过这一步（本来就不会跑复核）；读取异常一律按「不问」处理——宁可少问一次，也不能让弹窗挡住正常加载

弹窗放在**拿任务锁之前**：等待用户选择期间有 `await`，若客户端此刻断开、协程被取消，任务锁会永久占位（正常路径的锁由后台线程归还，而那时线程还没启动），之后所有任务都会被拒。顺带的好处是记录索引在弹窗之后才计算，不会因为等待期间新检测插入记录而点错行。

验证：`2026.09.11-2nd-partone.mp4`（5 球、缓存 MISS）点开后弹窗文案与两个按钮正常；选「直接加载」→ 日志 `[LOAD] cache=MISS | clips=5/5`、**无** `AI 复核补跑` 行、5 张卡片全无 AI 徽标、人工标签（keep 2 / reject 3 / 人物 2）照常恢复。新增 5 项单测（缓存未命中 / 全有分 / 部分缺 / 片段文件已删 / 无此记录）。

**批量回看刻意不问**（曾实现后回退，见提交 `14b8e1e` → 反向提交）：批量模式那两条入口（下拉框选视频 / 扫描文件夹后自动加载首个视频）同样存在「静默补跑」，一度也加了同款弹窗（探针 `batch_missing_scores` 快照优先）。回退原因：批量模式的正常流程是「扫描文件夹 → 标定 → 批量识别」，分数本就该由检测产生；在「点视频看一眼」时插一个问题时机别扭，而「开关关着就不问」时它又退化成一个多余的中转。现在批量回看缺分就缺分——要补分到历史记录里加载该视频（那里会问）。

#### 十三、标定文案澄清：框住的是「篮筐 + 篮网」

UI 一直写「标定篮筐」，但标定框在算法里从头到尾按**篮筐 + 篮网**在用，容易让人（包括写文档的自己）理解成只框筐圈。核对后统一改口径，**代码逻辑零改动**，只改文案与文档：

| 依据 | 说明 |
|---|---|
| 进球状态机 | 球的「筐上方 → 进框 → 筐下方」以框边界判定，且要在框内连续停留 2 帧（实测球在框内 2~4 帧）——只框筐圈时球一帧就穿过去了 |
| AI 三臂裁剪 | 短边 = 3.2 × 框高；框画小了裁剪窗跟着缩，视觉特征与训练口径错位 |
| 库里实测 | 27 场的框在 1080p 下约 100 × 110 px（高略大于宽、占画面高 8%~12%）；`recover_hoop2.py` 反推丢失标定用的统计中位正是「高 = 0.09 × 视频高」 |

改动：`demo_nicegui.py` 的标定提示与空列表引导、`services/detection.py` 的 5 条状态/报错文案（标定成功、重置、未标定拦截、批量未标定提示、保存标定前置检查）、`tracker.py` 的 `hoop_box` 参数文档、README 两处流程描述，并在 ALGORITHM.md 新增「标定口径」小节说明画小了的三处后果。

#### 十四、正样本也记来源：标签库两侧对称分流

上一轮已经把模型判的 × 分流到 `labels.auto_rejected`，但正样本没做对称处理：`_sync_marks` 把「所有 keep」不分来源写进 `labels.kept`，而 `build_dataset` 的 docstring 写着「只读 kept/deleted，即**人工**标签」——实际模型自动 √ 也在里面。实测缓存里现存 **121 个 `auto=True` 片段**（未经人工复核），而 `dataset_v1.json` 的 `label_source` 全是 `'ui'`，分辨不出来。

问题有三：高带精度约 0.99，即约 1% 的错误正样本被当人工真值固化且不可见；「模型替人省了多少」算不出来；历史回读时没有来源信息，旧自动 √ 会显示成人工 √（今天已踩到）。

改动（人工 / 模型两侧对称）：

| 来源 | 正样本 | 负样本 |
|---|---|---|
| 人工 | `labels.kept` | `labels.deleted` |
| 模型 | `labels.auto_kept` | `labels.auto_rejected` |

- `state.update_history_labels` / `get_labels` 增 `auto_kept`（`None` = 本次不改，与 kept/deleted 同语义）
- `detection._sync_marks` 按 `mark_source` 分流四种标记；历史回读与 `_restore_labels_to_clips` 恢复标记时**带来源**（优先级：人工 × > 人工 √ > 模型 √ > 模型 ×），自动 √ 不再被洗成人工
- **顺带修掉一个把分流整批撤销的旧调用点**：`clip_action` 的卡片 √/× 落盘以前写的是「所有 keep / 所有 reject」，人工每点一次卡片就把模型自动 √ 洗成人工正样本、把模型自动 × 写进 `deleted`——上一轮的负样本分流其实一直在这里被撤销。现在与 `_sync_marks` 共用同一个出口 `_split_marks_by_source`
- 重检测时模型标签**不搬旧 ts**（本次检测会重跑复核写新的），只抢救人工标签；`_remap_labels_to_goals` 在**任何返回分支之前**摘掉 `auto_*`——否则"只有模型标签、没有人工标签"的记录会走 `total==0` 的提前返回，原样带着陈旧 ts 进新记录（在训练集里变成该场根本不存在的假正样本）
- 新增 `state.label_sets(labels)`：导出 / 评估的统一口径 = 人工 ∪ 模型。整场集锦（`_clips_from_record`）与 4 个 eval 脚本全部改走它——只看 kept/deleted 会把模型自动 √ 当"未标注"，评估里变假阴性、整场导出直接丢球
- `build_dataset.from_history`：正样本取「人工 ∪ 模型」并写 `label_source`（`ui_manual` / `ui_auto`），负样本只取人工。模型自动 √ 默认收进来（正样本不够用）但来源可见，需要严格只用人工时按 `label_source == "ui_manual"` 过滤即可
- 本次改动之前的记录只有 kept/deleted、无法回溯来源 → 一律记 `ui_manual`，不猜

验证：
- 单测新增 7 项（来源往返 / `None` 不改 / 重检测丢弃模型标签 / 只有模型标签的记录重检测 / `_sync_marks` 四分 / 恢复带来源 / 卡片点 √ 不撤销分流），并扩了整场导出的并集断言
- `build_dataset.py --dry-run`：标注池 925 事件，**模型自动 √ 0 条**（旧记录还没产生过 auto_kept），与旧 dataset 的差异（+55）全部来自 `2026.08.31-2nd.mp4`（本会话刚检测完的那场，与本次改动无关）——即本次改动**没有悄悄改变训练集构成**
- 顺带记录一个待办：那 55 个事件（08.31-2nd 全场的 23 正 / 32 负）还没抽特征、没进训练集，下次训练前一并刷新

#### 十五、「点预览」即人工复核：零额外点击的来源升级

上一条把标签按来源分成人工/模型两侧后，立刻暴露出一个工作流矛盾：**AI 自动 √ 的片段，用户复核后不会去点"先取消再 √"**（那是重复操作），于是复核过的球永远记成 `ui_auto`——既算不出「模型替人省了多少」，改 `keep_thr` 时还会被当模型判断重算、可能打回「待确认」再让人看一遍。

中间试过两个方案（单击 √ 即确认、整带一键确认按钮），都要求用户为"记一笔"付出额外动作，不合习惯，已废弃（未提交）。最终按用户自己给的口径实现：

> 点「预览」就证明我在人工复核；我没改，就保留进人工来源，改了自然也是人工来源。

- `clip_action("preview", idx)`：该片段是 AI 已判（`mark_source == "auto"`，√ 或 ×）→ 只把来源升级为 `manual`，**标记值不动、选择集不动**，并落盘；状态栏回显「已记为人工复核（√/×）」
- 「AI 识别」关掉时**不**升级：那时卡片上看不到 AI 标记，预览不算"看了 AI 的判断"
- 未判定 / 已是人工来源的片段：预览不产生任何标记，行为与以前完全一致
- 顺带把落盘收成唯一出口 `_persist_marks(video_path, clips)`（`_sync_marks`、`clip_action` 的 √/×、新增的预览分支共用），杜绝以后再冒出"第三处把 mark 写回历史"时漏掉来源分流

验证：新增 1 项单测（AI √ / AI × 升级为人工且标记值不变、未判定不动、AI 关掉不升级）；`pytest tests` 134 项全绿。

#### 十六、留出集改成「整日留出」：08.31 作验证日，下一场新比赛作测试日

**先更正上一条结论**：我曾说「09.15 / 09.11 / 09.08 整天都不在训练集里」——错的，当时只查了 08.31/09.01/09.03 就外推。按天实际统计：09.01(62) / 09.03(40) / 09.04(225) / 09.08(160) / 09.11(217) / 09.15(166) 事件都在训练集里，**只有 08.31 是 0 事件**。

**问题**：原 `HOLDOUT` 是逐个**文件名**写死的 4 场（08.31-1st、09.01-3rd/-4th、09.03-3rd）。按文件名留出有个必然漏洞——**同一天新跑完的分节会悄悄进池**：08.31-2nd/-3rd 今天跑完时正走在入池路上。而「留出场与训练集共享同一比赛日」（同机位/同光照/同筐）正是留出集失去无偏性的原因，实测原来 4 场里已有 3 场这样。

**改动**（`training/build_dataset.py`）：
- 新增按**日期前缀**的整日留出 `HOLDOUT_DAYS = ("2026.08.31",)` + 统一判定 `is_holdout(name)`：前缀命中即整日排除，其余仍按文件名排除历史单场
- 分工写进 docstring：**08.31 = 调参验证日**（它参与过 `keep_thr` 0.72→0.75→0.68 的历史，只能算"见过的数据"）；**下一场新录的比赛 = 测试日**（整日留出、只跑一次、只报告、永不进训练；录完把日期前缀加进 `HOLDOUT_DAYS`）

**验证**：`build_dataset.py --dry-run` → 留出 6 场（08.31 三节 + 3 个历史单场），标注池 870 事件，**与现有 dataset 逐项一致（旧 870 → 新 870，新增 0 / 移除 0）**——这次留出策略调整对当前训练集零成本，不必重抽特征。

顺带修正一笔方法论（本节原先按**日期**判定，是错的）：自监督语料的判据是「该视频有没有被处理过」，不是录像日期——语料由 `frames_b` / `flow_b` 的**抽帧产物**构成，而这些目录只从 dataset 事件抽帧，没处理过的视频没有帧块可进池。两个编码器的语料范围也不一样：**B** = 8 月那批 `2232 events`（外部产物再导出，清单已丢失）、**Flow** = 9 月这批 `831 events`（本仓库 09-19 训）。修正后的结论：不是"08.31 之前的比赛日可能进过语料"，而是**任何被处理过的日子都在某个编码器的语料里**；要挑独立测试日，只能取从未处理过的新比赛（如新录一场）。

| Maxwell / Pascal / Volta / Turing / Ampere / Ada | sm_50 ~ sm_89 | ✅ | ✅ |
| **Blackwell（RTX 50 系）** | **sm_120** | ❌ | ✅ |

> ⚠️ torch ≥ 2.11 的 cu128 构建已移除 Maxwell/Pascal/Volta，如需覆盖 GTX 10 系及更老显卡必须固定 `torch==2.7.1`。`requirements.txt` 已写明该约束与原因。

#### 三、PyAV 解码容错（开头 NAL 损坏但后续数据完好的视频）

**问题现象**：20240824 金纺 1st quarter.mp4 等录制断电/存储异常的 HEVC 视频，ffprobe 能读到元信息（40734 帧/1080p/HEVC），但解码首包就报 `Invalid NAL unit size - Invalid data found when processing input`，PyAV 默认 container.decode 直接抛 `InvalidDataError` → 预览帧为 None → UI 报加载不出视频。

**修复**：`video_io.py` 两条解码路径统一换为 `container.demux` + `codec_context.decode(packet)` 逐 packet try/except 容错：

| 函数 | 旧逻辑 | 新逻辑 |
|------|--------|--------|
| `read_frame(path, idx, ...)` | `container.decode(stream)`（任一 NAL 损坏即整个 seek 失败返回 None） | `for p in demux: try: cc.decode(p) except: continue`（跳过损坏 packet，找到目标帧即返回） |
| `VideoReader.iter_frames(start, end, batch)` | 同上（损坏视频整个检测阶段无法推进） | 同上（对 GoalDetector 处理流程透明，帧号按 pts 计算仍正确） |

- 正常视频零损坏 packet → try/except 不触发 → **零性能影响**
- 实测 20240824 金纺：跳 309 个损坏 packet 后从首个完好 GOP 解出帧，后续 40000+ 帧全正常，检测流程可完整跑完
- `-err_detect ignore_err` 的 ffmpeg CLI 转码方案也可作为预处理，但 PyAV 层内置容错对用户透明（无需先修视频）

#### 四、帧选择器（标定前拖动滑条选帧 + Catch-up 防抖）

加载视频成功后，预览画面下方显示帧滑条与帧号标签（`帧 N / 总帧数  MM:SS.m`）：

- **显隐同步**：只有「preview」面板（预览图 + 已加载多帧视频）时才显示帧选择器；result/highlights/progress 面板自动隐藏
- **三处加载同步**：单视频 `_on_load`、批量 `_on_batch_load_video`、历史 `_on_load_history` 成功后均调用 `_sync_frame_selector` 同步滑条 min/max/value
- **Catch-up 选帧策略**：拖动过程 `on_value_change` 事件密集，`read_frame` 昂贵（开容器+seek+解码 ≈ 数百 ms）。解码进行中收到新事件只记 `_frame_sel["pending"]`，当前解码完成后直接一次跳到 pending 最新值，不排队解码拖动路径所有中间帧 → 手感顺滑无积压
- **`current_frame` 同步**：滑块目标帧会写入 `state.video_state["current_frame"]`，与「标定点击画面 2 个点」逻辑的基准帧采集对齐——用户拖到有清晰篮筐的帧再标定，不必再找正好是第 0 帧的画面
