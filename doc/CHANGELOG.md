### 2026.09.05 整场集锦导出（四节合并）

个人集锦不再局限于单节——跨视频合并同一人物整场片段。

#### 一、多源切片（cutter/ffmpeg_cutter.py）

- `cut_clips` 支持多视频源：`[(视频路径, [ts,...]), ...]`
- **各源独立合并相邻片段**：不同视频时间轴不连续，禁止跨源合并（即使 min_gap 再大）
- 按源顺序（第1节→第4节）流拷贝拼接，NVENC/软编容错与单源一致
- 真实 ffmpeg 端到端测试：合成视频验证多源时长、跨源不合并回归

#### 二、整场导出（services/detection.py `generate_highlights_fullgame`）

- **视频集合**：批量模式 = 扫描过的文件夹；**单视频模式 = 自动回退扫描当前视频所在文件夹**（单视频加载会清空 batch_files，不扫文件夹也应能整场导出）
- 片段来源优先级：流水线快照（本轮批量最新）→ 历史记录（`_clips_from_record` 轻量重建，不生成预览）
- **round(ts,3) 舍入匹配修复**：历史记录 goals 存全精度（31.278908）而标签键存 round(3)（"31.279"），精确匹配必失败导致筛不到任何片段——按历史加载路径的舍入规则对齐
- 人物筛选规则与单视频一致（有√只导√ → 无√排除× → 无标记导筛选池全部），无记录视频自动跳过
- 输出 `{文件夹名}-{人物}-highlights.mp4`（如 `2026.09.04-智-highlights.mp4`），与各单节导出互不覆盖；无公共目录回落 `{首视频名}-game-`

#### 三、UI（demo_nicegui.py）

- 导出行新增「整场集锦」按钮（与「导出集锦」并列），tooltip 说明合并规则
- 人物下拉并入全局名单：单视频模式查看第3节时也能直接选「小明」（他只在第2节进过球）
- 流水线模式共用 hl_busy 小锁 + 独立取消事件，不打断后台批量检测

### 2026.09.05 缺陷修复（断点续跑 / 自适应阈值 / 标签数据完整性）

### 2026.09.05 人物分类工作流（片段归属 + 按人物导出集锦 + 跨场次复用）

#### 一、卡片人物分类徽章 + 分类对话框

- 每个进球卡片第一行右侧新增 `👤 分类` 胶囊按钮；已分类显示 `👤 人物名`
- **8 色调色板**（cyan/violet/pink/amber/green/orange/sky/fuchsia），按人物名排序循环分配，同屏人物不撞色；徽章/对话框/统计行三处同源着色
- 分类对话框（persistent）：已有人物快捷 chips + 输入新人物名（回车确认）+ 清除分类
- 顶部统计行显示各人物进球数（彩色胶囊）

#### 二、集锦按人物导出

- 导出行新增人物筛选下拉：`全部人物` / `仅已分类（N）` / 各人物（带计数）
- 筛选与 √/× 规则叠加：先筛出该人物（或已分类）的片段池，再按「有√只导√ → 无√排除× → 无标记全导」
- **输出文件名带人物名**：`{视频名}-{人物}-highlights.mp4`（如 `2026.09.04-2nd-小明-highlights.mp4`），多人物个人集锦互不覆盖；「仅已分类」导出为 `{视频名}-已分类-highlights.mp4`
- 人名文件名安全化：Windows 非法字符剔除 + 截断 30 字符 + 全非法回落 `person`

#### 三、全局人物名单（跨场次复用）

- `cache/persons.json` 持久化全局名单，与单视频 `labels.persons` 分离
- 分类时自动登记，最近使用在前，重复使用提到队首
- 对话框分两组展示：**本视频人物**（彩色 chips，与卡片徽章同色）/ **其他场次人物**（灰色 chips，按最近使用排序）——周一在 A 场次创建的「小明」，周三打开 B 场次直接点选

#### 四、人物标签持久化与重跑重映射

- 分类存入历史 `labels.persons`（`{进球ts: 人物名}`），与 √/× 标记同文件、增量写互不覆盖
- 三条加载路径（单视频 / 批量快照 / 批量历史）自动回填分类
- 改参数重跑后，人物分类与 kept/deleted 一样按 ±0.5s 容差自动重映射到新时间戳
- 流水线模式（批量检测运行中）对快照视频分类同样安全并持久化

#### 五、批量标定跨会话复用

- **问题**：批量模式标定只存内存 `batch_calibs`，重启/重扫描后全部丢失，即使历史记录里存着每个视频的 `hoop + baseline_idx`
- **修复**：扫描文件夹时 `backfill_batch_calibs_from_history()` 从历史整体回填（列表直接显示 ✓ 已标定，可直接批量识别）；单个视频加载时兜底恢复（`state.get_record` 单文件直读）；本次会话新保存的标定优先，不被历史覆盖

测试 71→73 项全通过（新增名单登记/去重/最近使用、回填优先级、导出命名/过滤等 12 项用例）。

### 2026.09.03-04 ad 分支增量更新（人工标记工作流 / 帧选择器 / HEVC 容错解码 / 标签飞轮）

本轮更新围绕「**高召回候选 + 人工确认**」工作流落地，解决旧版 YOLO 硬否决门槛过高导致候选被整体丢弃、人工无法筛选的问题；同时补齐片头损坏 HEVC 视频的解码容错与帧选择器体验。

#### 一、进球卡片交互重做（删除 → √ 确认 / × 误报 + 动态样式）

| 项 | 旧版 | 新版 |
|---|------|------|
| 卡片按钮 | 预览 / 导出 / 删除（误报直接从列表消失，无法恢复或回看） | **预览 / √ 确认 / × 误报 / 导出**（片段完整保留，仅做标记，再次点同按钮 = 取消标记） |
| 视觉反馈 | 无 | √ 标记后卡片**绿色边框 + 浅绿底色**，× 标记后卡片**红色边框 + 55% 透明度半透明** |
| 顶部统计行 | 无 | 卡片列表顶部显示 `√ N · × N · 待标 N`，右侧同步导出说明（只导 √ / × 排除 / 未标全导） |
| 集锦生成逻辑 | 删除即从 clips 移除 | 优先导出 √ 标记片段；无 √ 但有 × 则导出未标片段；完全没标记时全导（向后兼容） |
| 空状态文案 | 「该视频的片段已全部删除」 | 「该视频暂无片段」 |

**UI 改动文件**：`demo_nicegui.py`（卡片渲染 + `_on_mark_clip` 替代 `_on_delete_clip` + 三处加载路径同步）

#### 二、检测状态与标签飞轮持久化（`clip_action` / `update_history_labels`）

- `services/detection.py` — `clip_action` 的 `delete` 分支替换为 `mark_keep` / `mark_reject`
  - `clip["mark"] = "keep" | "reject" | None`（toggle：再点同按钮取消）
  - `clip["mark_source"] = "manual"`（有值代表人工确认过，训练池可直接用）
  - `kept` 集合（用于集锦）统一以 mark=="keep" 的片段重建
- `services/state.py` — 新增 `_find_history_record` + `update_history_labels`
  - `_find_history_record`：精确匹配 video 路径优先，失败后按**文件名兜底**（视频迁移目录后历史记录仍能命中，避免新建记录导致训练池标签/标定断档）
  - `update_history_labels`：**增量写 labels 字段**，不重建整条记录，不丢检测元信息（`kept` / `deleted` 时间戳 + `label_time`）
  - 标记完成后原记录上浮到 detection_history.json 顶部（最近更新优先）

#### 三、PyAV 解码容错（开头 NAL 损坏但后续数据完好的视频）

**问题现象**：20240824 金纺 1st quarter.mp4 等录制断电/存储异常的 HEVC 视频，ffprobe 能读到元信息（40734 帧/1080p/HEVC），但解码首包就报 `Invalid NAL unit size - Invalid data found when processing input`，PyAV 默认 container.decode 直接抛 `InvalidDataError` → 预览帧为 None → UI 报加载不出视频。

**修复**：`video_io.py` 两条解码路径统一换为 `container.demux` + `codec_context.decode(packet)` 逐 packet try/except 容错：

| 函数 | 旧逻辑 | 新逻辑 |
|------|--------|--------|
| `read_frame(path, idx, ...)` | `container.decode(stream)`（任一 NAL 损坏即整个 seek 失败返回 None） | `for p in demux: try: cc.decode(p) except: continue`（跳过损坏 packet，找到目标帧即返回） |
| `VideoReader.iter_frames(start, end, batch)` | 同上（损坏视频整个检测阶段无法推进） | 同上（对 GoalDetector 处理流程透明，帧号按 pts 计算仍正确） |

- 正常视频零损坏 packet → try/except 不触发 → **零性能影响**
- 实测 20240824 金纺：跳 309 个损坏 packet 后从首个完好 GOP 解出帧，后续 40000+ 帧全正常，检测流程可完整跑完
- `-err_detect ignore_err` 的 ffmpeg CLI 转码方案也可作为预处理，但 PyAV 层内置容错对用户透明（无需先修视频）

#### 四、帧选择器（标定前拖动滑条选帧 + Catch-up 防抖）

加载视频成功后，预览画面下方显示帧滑条与帧号标签（`帧 N / 总帧数  MM:SS.m`）：

- **显隐同步**：只有「preview」面板（预览图 + 已加载多帧视频）时才显示帧选择器；result/highlights/progress 面板自动隐藏
- **三处加载同步**：单视频 `_on_load`、批量 `_on_batch_load_video`、历史 `_on_load_history` 成功后均调用 `_sync_frame_selector` 同步滑条 min/max/value
- **Catch-up 选帧策略**：拖动过程 `on_value_change` 事件密集，`read_frame` 昂贵（开容器+seek+解码 ≈ 数百 ms）。解码进行中收到新事件只记 `_frame_sel["pending"]`，当前解码完成后直接一次跳到 pending 最新值，不排队解码拖动路径所有中间帧 → 手感顺滑无积压
- **`current_frame` 同步**：滑块目标帧会写入 `state.video_state["current_frame"]`，与「标定点击画面 2 个点」逻辑的基准帧采集对齐——用户拖到有清晰篮筐的帧再标定，不必再找正好是第 0 帧的画面

#### 五、工作流整体影响（检测 → 标签 → 训练池）

| 环节 | 旧版 | 新版 |
