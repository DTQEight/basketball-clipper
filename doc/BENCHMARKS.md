### 2026.09.01-1st.mp4 解码线程优化前后对比（2026.09.19，FRAME vs SLICE）

对比数据来源：同一视频、**同参数**（`ball_conf` 0.15 / `min_gap` 2.0s / `yolo_step` 3 / 条件跳过开 / `imgsz` 1280）、**同标定**（`[1360, 338, 1426, 424]`，基准帧 0），仅切换 PyAV 解码线程模式。视频 1080p 30.05fps，999.2s，30,027 帧。

#### 一、核心性能指标对比

| 指标 | SLICE（原） | FRAME（新） | 差异 |
|---|---|---|---|
| ⏱ 检测耗时 | 416.4s (06:56) | **305.2s (05:05)** | **−26.7%** ✅ |
| 🚀 处理 FPS | 75.9 | **105.8** | **+39.4%** ✅ |
| ⚡ 实时速度比 | 2.53× | **3.52×** | **+39.1%** ✅ |
| 🎯 YOLO 调用次数 | 1,318 | 1,318 | 0 |
| ⏭ YOLO 跳过率 | 86.8% | 86.8% | 0 |
| ✅ YOLO 确认进球 | 28 | 28 | 0 |
| ❌ YOLO 拒绝数 | 137 | 137 | 0 |
| 📦 处理帧数 | 30,027 | 30,027 | 0 |
| 📐 自动阈值 | 19 | 19 | 0 |
| 🏀 候选进球 | 28 | 28 | **逐项完全一致（3 位小数）** |

**小结**：这是一次纯粹的管线优化 —— 全部检测统计指标逐项相同、28 个候选时间戳完全一致、人工标签（19 kept / 8 deleted）原样保留，**耗时减少 111 秒（−26.7%）**。

#### 二、耗时拆解（定位瓶颈）

| 环节 | 耗时 | 占比 | 实测速率 |
|---|---|---|---|
| 逐帧解码 | 247.8s | **60%** | 121.2 帧/秒 |
| YOLO 1318 次 @1280 | 93.7s | 23% | 71.1 ms/次 |
| 其余逐帧 CV | 74.9s | 18% | 2.50 ms/帧 |

**瓶颈不在检测算法，而在解码**：YOLO 只占 23%，逐帧解码占 60%。此前所有性能优化（`imgsz`、置信度、条件跳过）动的都是那 41%。

#### 三、解码模式基准（2000 帧实测，i5-10200H / GTX 1650）

| 配置 | 帧/秒 | 全片 30,027 帧推算 |
|---|---|---|
| SLICE（PyAV 默认，原） | 130.0 | 231.0s |
| **FRAME** | **285.1** | **105.3s** |
| AUTO（等价于 FRAME） | 276.9 | 108.4s |
| ffmpeg CLI（不转 bgr24，参考上限） | 610 | 49.2s |

- FRAME 相对 SLICE **快 2.19×**；AUTO 与 FRAME 基本等价
- 纯解码 193.3 帧/秒 → 含 `to_ndarray(bgr24)` 141.9 帧/秒：像素格式转换本身吃 **27%**（约 1.87 ms/帧，换不掉，OpenCV 需要 BGR）
- 与 ffmpeg CLI 的 610 帧/秒仍有差距（后者不转像素格式且可跨帧调度）

#### 四、等价性验证（`cache/_thread_check.py`）

两种线程模式解出的**帧号与整帧像素 MD5 完全一致**，覆盖四条路径：

| 路径 | 对照量 | 结果 |
|---|---|---|
| 顺序解码 `start=0` | 600 帧 | 全部一致 |
| `seek()` 到任意帧后解码 | 8 个 seek 点 × 30 帧 | 全部一致，首帧精确等于 seek 目标 |
| `read_frame()` 单帧抽取 | 10 个帧号（含 GOP 内部 1/7/33） | 全部一致 |
| 多段连续 seek（模拟断点续跑） | 6 段 × 20 帧 | 全部一致 |

代价：每线程缓冲一帧，1080p yuv420p 约 3.1MB/帧，8 线程多占约 **25MB**。

#### 五、换参数重跑（非同口径，仅供参考）

用户以 `ball_conf` 0.2 + 重新标定的筐框 `[1353, 339, 1447, 446]`（面积 1.8×）+ 基准帧 9683 重跑：

| 指标 | 基线（SLICE） | 本轮（FRAME） |
|---|---|---|
| ⏱ 检测耗时 | 416.4s | **331.3s（−20.4%）** |
| 🚀 处理 FPS | 75.9 | **98.8** |
| 🎯 YOLO 调用次数 | 1,318 | 1,671（+27%） |
| 🏀 候选进球 | 28 | 34 |
| ✅ 命中已知 19 真球 | 19/19 | **19/19** |

提速 1.30× 是**在更重负载下**（YOLO 调用多 27%、搜索框面积 1.8×）拿到的。候选数 28 → 34、误报 9 → 15 来自参数松动（自适应阈值 19 → 16 叠加筐框变大），**与线程改动无关** —— 同口径那一版（上文第一节）28 个候选逐项一致可作反证。

> 注：该轮 `warmup_p95_median` 由 11.0 变为 8.0，原因是基准帧从第 0 帧换到 9683 帧导致预热采样画面不同，非异常。

5. 建议**再跑 2026.08.15-1st.mp4 和 2nd.mp4 两次对比**，把 ad vs 旧的"漏检分布 / 漏检率 / 质量趋势"量化出来，再决定是否合 main（3rd 少 1 球、4th 少 4 球 —— 如果 1st+2nd 也呈少球趋势，那就是质量系统性下滑，需要拉警报先修）

| 6 | 接受框几何 | 内联在 `_check_yolo_near_hoop` 内 | 抽成 `yolo_accept_box()`，判定端与检测端共用（裁剪范围必须 ⊇ 它） |
| 7 | 远端误报 | 会进模型输入（靠「球框保留全部」的修复兜住） | 天然落在输入之外（附带收益） |
| 8 | 标定口径（文案+文档） | 「篮筐」「篮筐框」 | 「篮筐+篮网」「框住筐与网；上/内/下都以这个框的边界为准」 |

> 1+2 是**同一处**改动的「判据」与「保证」；3–7 属于**裁剪推理**及其配套重构；8 只改文案/文档，不改变算法，但会改变用户的标定实践 → 间接影响结果。

#### 三、两处行为改动的实测代价 / 收益

**① 条件跳过判据（影响召回）**

|---|---|

**② 裁剪推理（影响耗时）** —— 09.11-1st，同门槛同参数，只切输入路径

**③ 裁剪推理的已知漏检风险（2026.09.21，08.31-3rd 实测）**

09.11-1st 的 A/B 里裁剪路径「候选 / 真球 / 误报全部不变」，但那是单场、球也偏大。08.31-3rd 出现一例**真球静默漏检**（用户确认 `449.16s` 为真进球）：

| 环节 | 观测 |
|---|---|
| 条件跳过门 | 全程开着（ROI 内运动 800~3000px）→ **不是门的问题** |
| 该窗口 YOLO | 12 次调用**全部返回 0 个球框** |
| 同帧同模型对照 | 整帧@1280 六帧命中 4（conf 0.64~0.81）；裁剪@640 命中 **0**（唯一一次 0.22）；裁剪@768/960/1280 也检不出（只出腿部误报） |
| 裁剪图内容 | 球清晰可见（贴在篮板上沿）→ **内容没问题** |
| 决定性实验 | 把接受框外抹黑、**保留整帧画布**后：@1280 结果与整帧完全一致，@640 也命中 5/6（0.39~0.84） |

结论：**把裁剪出的小图单独送进模型，会让部分小球的置信度掉到阈值以下**（与训练分布的画面尺度/宽高比不一致），再叠加「每 3 帧才跑一次 YOLO」的相位，就整球没有候选。

单变量实测（帧 0~455s，同相位、同预热；base 与正式运行逐球一致）：

| 变量 | 候选 | 449.16 | 耗时 |
|---|---|---|---|
| 现状（ball_conf 0.2 / in_hoop 2 / circ 0.35 / step 3 / 窗口 0.34s） | 15 | **漏** | 108s |
| **ball_conf 0.2 → 0.15** | 16 | **命中** | 100s |
| **yolo_step 3 → 2** | 16 | **命中** | 109s |
| min_in_hoop_frames 2 → 1 | 16 | 漏 | 101s |
| min_circularity 0.35 → 0.25 | 16 | 漏 | 101s |
| YOLO 确认窗口 0.34s → 0.68s | 16 | 漏 | 101s |

进框帧数 / 圆形度只管斑块，管不到 YOLO 硬否决；加长确认窗口无效（`ball_pos_history` 里根本没有球）。**两条能命中的都只是「让采样对准那一帧」，不是治本**。

**2026.09.21 已解决（两段式兜底）**。按「改推理输入」的方向实测，挖矿量化了问题的普遍性（4 场 / 80 个真球 / 2467 帧）：整帧@1280 认得出而裁剪@640 认不出的「真硬帧」有 518 个，且 **80/80 个真球事件都含真硬帧**；真·裁剪@640 在这些帧上命中 **0%**。三种输入路径的同批对比：

| 输入路径 | 真硬帧 ≥0.5 | 正常帧被弄坏 | 单次推理 |
|---|---|---|---|
| 真·裁剪@640（原线上） | 0 / 518 | 0 / 180 | ~22 ms |
| 抹黑画布@640（原以为"同速等效"） | 334（64%） | 34% | ~22 ms |
| 抹黑画布@1280 | 482（**93%**） | 6% | ~45 ms |

（抹黑@640 之所以不行：1920→640 后球只剩 ~6.7px；真裁剪的问题则是几何——竖版 488×583 小画布 vs 训练的 16:9。）

但**全局换抹黑@1280 不划算**（库里 5 场 A/B）：真球净只 +1（±1.5s 102→103）、误报 +2，却要 **+14.5% 检测耗时、候选 +13%**——因为事件级召回对单帧分数不敏感（状态机只要窗口里有一帧过阈值就够）。最终落地**两段式**：默认仍走裁剪@640，只在轨迹即将被 YOLO 硬否决（整窗无证据）时用抹黑@1280 补检一次，且只采信 `conf ≥ 0.5` 的证据。6 场实测：真球 **116/119 → 119/119**、误报 147→150、候选 +8.8%、耗时增量被网络盘读帧噪声盖住（补检本身约占 1.7%，含 136 次被门槛挡下的低分证据）。

#### 四、小结

- 识别路径上只有 **两处行为改动**：① 条件跳过判据替换、② 裁剪推理（输入范围 + imgsz）；其余为重构（第 6 项）与文案（第 8 项）
- **模型权重、进球判定状态机、断点续识别、自适应阈值预热、解码路径全部一致** —— 两条线的识别差异不涉及模型本身
- **已同步**：第 1–7 项 2026.09.21 合入 main（`27a01a1` / `2d11725` / `3cc10f3`），两条线的检测路径一致；仅第 8 项（纯文案）仍只在分支
- 遗留：裁剪推理存在「小球置信度被压低 → 偶发整球无候选」的风险（见上「③」）——2026.09.21 已用**两段式兜底**堵住（默认裁剪 + 即将被否决时抹黑画布补检），并已同步到 main（`0b0b670` + `7ac1cd4`），发布线不再有此缺口

## 篮球检测权重三代对比与双盲测日方法论（2026.09.21）

### 一、样本配方（`training/build_yolo_crop_dataset.py`）

按「部署几何」造样本，无需人工标注：老师＝现役模型在**整帧**上的 `conf=0.05` 预测；学生样本＝`筐接受框 + 20% 外扩`的裁剪块，标签由老师框投影到裁剪坐标系（中心落在块外 → 该样本变成裁剪画布下的**背景样本**）。每帧同时产出整帧版与裁剪版，`imgsz=640` 后球在两版里分别约 8px / 22-33px，正对应线上「主档 crop@640」与「兜底 mask@1280」两种推理尺度。

### 二、盲测纪律（本次的关键方法论）

1. **盲测日整天排除**：`--blind=08.31,09.11`，这两天的视频不进训练也不进验证
2. **val 只做训练监控**：另取事件数最少的 2 场当 val，**不能拿来判断泛化**（本次 val mAP50 0.62 与盲测结论无关）
3. **判据是端到端**：帧级分数只用来定位问题，最终以「真球 ±1.5s 命中 / 候选数 / 误报被检 / 耗时」四件套在盲测日上判
4. **A/B 都要实跑**：基线不能用 `cache/history`（每场只留最后一次运行，可能是旧版产物）；裁剪档虽逐位可复现，但换的是**模型权重**时基线会变，必须当场跑 A 轮
5. **同一协议对比**：生产已有兜底，A/B 都必须开 `--prod`，否则「兜底带来的增益」会被记到「新权重」头上

### 三、三代权重

| 版本 | 训练视频 / 图 | imgsz | 帧级：08.31 硬帧裁剪@640 | 端到端（生产配置） |

**结论**：① 扩库（10 场 → 23 场）没有牺牲第一盲测日，且回归代价从 +5.2% 降到 +2.2%（**精度同时变好**）；② 边际收益在轮数上很低——1 轮就能到 97%、6 轮 99%，**不要再堆轮数**；③ 09.11 只有 91%（低于 08.31 的 99%），差距在**机位/场地的样本多样性**，不在轮数，下一步要投的是覆盖更多机位。
